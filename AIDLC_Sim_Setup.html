Step 1
🧭 Orientation

AIDLC is no longer a folder of rule files

Our March 2026 guides had you copy core-workflow.md into .github/copilot-instructions.md and a folder of phase rules into .aidlc-rule-details/. The upstream project (awslabs/aidlc-workflows) has since become a native engine: one installed command, aidlc, that projects a full runtime (hooks, agents, skills, scopes, sensors) into each repo and enforces the workflow deterministically.

⚠️

Visual Studio 2022 is not a supported surface. The Copilot harness relies on hook and skill features that exist only in VS Code ≥ 1.130 (agent mode) and Copilot CLI ≥ 1.0.74. Keep Visual Studio for editing and debugging, and run AIDLC from VS Code, the Copilot CLI or Claude Code.

What you'll have at the end

One machine install

aidlc on your PATH with every harness runtime. No Bun or Node.js needed.

Two harnesses, one repo

.claude/ for Claude Code and .aidlc/ + .github/ for Copilot share one aidlc/ workspace.

Hooks you can trust

Approval gates, audit, sensors and guards run as hooks, so the workflow holds even when the model gets creative.

A clean doctor

aidlc doctor and /aidlc --doctor both green before your first workflow.

✅ Checklist

Before you start

The native runtime needs nothing extra. Your harness (the AI tool) still has its own requirements. Pick the tools your team will use:

  • ✓
    Claude Code installed and signed in: subscription, API key, Amazon Bedrock or an enterprise gateway. AIDLC keeps whatever provider you already use.
  • ✓
    Project hooks allowed. If your organisation sets allowManagedHooksOnly, project hooks are blocked and /aidlc --doctor will say so.
  • ✓
    VS Code ≥ 1.130: check with code --version. VS Code agent hooks are a Preview feature.
  • ✓
    Copilot Business/Enterprise sign-in (or a Custom Endpoint provider). AIDLC pins no model: every agent uses your chat's model.
  • ○
    Org policy allows "Chat: Use Hooks" (chat.useHooks). Your organisation can turn it off; if it does, gates go unrecorded.
  • ✓
    Copilot CLI ≥ 1.0.74: check with copilot --version. Install with npm install -g @github/copilot.
  • ✓
    GitHub sign-in or BYOK (for example Amazon Bedrock via COPILOT_PROVIDER_BASE_URL + COPILOT_PROVIDER_TYPE).

For everyone

  • ✓
    A normal (non-admin) terminal. The installer is per-user. An elevated "Run as administrator" window gets a warning and a prompt.
  • ✓
    Git + Azure DevOps contributor access to the repo, and a feature branch you can raise a PR from.
  • ○
    Optional: GitHub CLI (gh). With it, the installer also verifies the signed release attestation; without it, SHA-256 checksums are still verified.

Prefer to read a script before running it? Download first: irm …/install.ps1 -OutFile install.ps1, review it, then run powershell -ExecutionPolicy Bypass -File install.ps1. Use -NoModifyPath to skip PATH changes and -Version 2.11.0 to pin a release.

bash / zsh

The machine install never touches a repo. Projects get their files from aidlc config in the next steps, and aidlc update later updates only the machine.

🟣 Harness 1

Configure the repo for Claude Code

Run from the repo root. config is local and transactional: it writes the harness runtime, creates the aidlc/ workspace, merges into files you already own and records what it owns for later refreshes. Add --dry-run to preview.

PowerShell: C:\dev\billing-service
PS> aidlc config --harness claude configured C:\dev\billing-service for Claude Code 2.11.0; next: open Claude Code in this project (if it is already open in this folder, exit it and start it again) and run `/aidlc --doctor`

🔐 Trust

Let each tool run the project's hooks

Gates, the audit trail and the guards are hooks. If a tool silently skips them, approvals can't be recorded. Each surface has its own trust switch:

  1. Start claude in the repo. Approve the project hooks when prompted (or later via /hooks).
  2. If Claude Code was already open in this folder, exit and start again. /clear is not enough.
  3. If the doctor reports disableAllHooks, override it with "disableAllHooks": false in your local Claude settings file.
  1. Open the folder and choose Trust (VS Code Workspace Trust).
  2. aidlc config already set "chat.useHooks": true in .vscode/settings.json. The folder value wins over a user setting that is off, but an organisation policy can still disable it.
  3. VS Code never reads the Copilot CLI trust list, and a skipped hook leaves no chat message. Since 2.11, AIDLC's first reply stops and tells you when no hook ran (look in the Agent Debug Logs panel).
  1. Run copilot interactively once in the repo and choose "Yes, and remember this folder for future sessions". That adds the folder to trustedFolders in %USERPROFILE%\.copilot\config.json. AIDLC never edits that file for you.
  2. Headless runs (copilot -p) additionally need the environment variable GITHUB_COPILOT_PROMPT_MODE_REPO_HOOKS set to 1, or every hook silently does nothing.

Record that the team reviewed the allowlists

PowerShell
PS> aidlc config trust --harness copilot --show Trust configuration for copilot Allowlist reviewed: not recorded Trust and allowlist files: C:\dev\billing-service\.aidlc\tools\data\harness.json C:\dev\billing-service\.github\hooks\aidlc.json C:\Users\marcus.l\.copilot\config.json Unmet: copilot-folder-untrusted - Copilot CLI has not trusted this folder PS> aidlc config trust --harness copilot --acknowledge --yes Trust recorded allowlist review acknowledgement Recorded the trust answer in .aidlc/tools/data/harness.json. To undo: aidlc config trust --reset --yes --harness copilot PS> aidlc config trust --harness claude --acknowledge --yes
⚠️

With two harnesses present, the trust, models, providers and flags subcommands need --harness <name>. Without it they stop with "multiple project harnesses are present; pass one --harness <name>".
