OpenAI Codex: Training Path

Six modules from the local CLI to cloud fan-out and CI. About 8.5 hours in total, with a lab in each module and a knowledge check at the end.

L100 → L300~8.5 h6 labs12-question check
⌂ All guides
ℹ️

Before you start: read the Onboarding guide. Labs need the Codex CLI signed in, a sandbox repo with tests, and a workspace with Codex cloud enabled and a GitHub connection.

Modules

L100

M1 · Codex surfaces and when to use each

45 min
  • CLI, IDE extension, cloud tasks, GitHub review, codex exec, SDK.
  • Local (steer) vs cloud (delegate, parallel, attempts).
  • What stays human: scope, design, merge, production.
Lab 1: Do the "pick a surface" exercise in Sim 3, then classify your team's last 10 tickets.
L100

M2 · Sandbox, approvals and config

90 min
  • Sandbox modes (read-only, workspace-write, full access) and network access.
  • Approval policies and the in-session permissions menu.
  • config.toml (user vs project), profiles, trusted projects.
Lab 2: Create explore and build profiles. Prove that explore can't edit and build asks before network access.
L200

M3 · AGENTS.md, skills and MCP

90 min
  • AGENTS.md discovery from global to nested; overrides; keeping it short.
  • Skills in .agents/skills/, invoked with $name or chosen automatically.
  • MCP servers in config or via codex mcp add; least privilege.
Lab 3: Write a root and a nested AGENTS.md plus one skill. Show that the nested rule wins inside its folder.
L200

M4 · Codex cloud: environments, tasks, attempts

2 h
  • Environment setup scripts, variables, setup-only secrets, agent internet access.
  • Writing delegable tasks; multiple attempts; follow-ups; creating PRs.
  • Reviewing many diffs without becoming the bottleneck.
Lab 4: Build an environment whose setup fails fast. Run one task with 3 attempts and write down why you picked the one you did.
L300

M5 · Review and automation

90 min
  • /review locally; @codex review and automatic reviews; review guidelines in AGENTS.md.
  • codex exec and the GitHub Action: read-only triage, structured output.
  • Treat logs and issue text as untrusted input.
Lab 5: Add a read-only failure-explainer step to a pipeline and break a test to trigger it.
L300

M6 · AI-DLC on Codex

90 min
  • aidlc config --harness codex, $aidlc, the record in aidlc/.
  • Units → cloud tasks; pushing the record so containers can read it.
  • When the method is worth it and when a single task is enough.
Lab 6: $aidlc … --scope express on a toy feature; send one Unit to the cloud.

Knowledge check

1. What's the difference between the sandbox and the approval policy?

2. A sensible team default for local work?

3. Which file does Codex read for repo instructions?

4. How do you start AI-DLC in Codex?

5. In a cloud environment, when is internet available by default?

6. When are multiple attempts worth it?

7. A cloud task can't find your AI-DLC functional design. Most likely cause?

8. Where do you put rules that @codex review should check?

9. Safe way to have Codex explain CI failures?

10. Why treat CI logs as untrusted input?

11. How do you switch quickly to a read-only setup?

12. The team runs 30 cloud tasks a day and PRs pile up. Best fix?
