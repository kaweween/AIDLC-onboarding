🛡️ Permissions

Commit team permissions in .claude/settings.json

Rules are checked in this order: deny wins, then ask, then allow. Managed (org) settings outrank project settings, which outrank your personal ones.

.claude/settings.json (permissions)
{ "permissions": { "allow": ["Bash(dotnet build:*)", "Bash(dotnet test:*)", "Bash(git diff:*)", "Bash(git status)"], "ask": ["Bash(git push:*)", "Bash(dotnet ef database update:*)"], "deny": ["Read(./.env)", "Read(./secrets/**)", "Bash(curl:*)", "Bash(az * delete*)"] } }

Try it: what happens to this tool call?

🪝 Hooks

Make the important rules deterministic

A hook is a command the harness runs at a lifecycle event. A PreToolUse hook that exits with code 2 blocks the action and tells Claude why. A PostToolUse hook can format files after every edit.

.claude/settings.json (hooks)
{ "hooks": { "PreToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": ".claude/hooks/block-migrations.sh" }] }], "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": ".claude/hooks/format-edited.sh" }] }] } }
.claude/hooks/block-migrations.sh
#!/usr/bin/env bash path=$(jq -r '.tool_input.file_path' ) # hook input arrives as JSON on stdin if [[ "$path" == */Migrations/* ]]; then echo "Migrations are generated. Run: dotnet ef migrations add <Name>" >&2 exit 2 # 2 = block, message goes back to Claude fi
⚠️

Hooks run with your user's permissions. Review hook scripts like any other code, and check the current hook input fields in the docs before you rely on them.
