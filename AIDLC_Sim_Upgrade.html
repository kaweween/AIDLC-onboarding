⛔

Don't just install v2 on top and leave v1 in place. v1's core workflow opens with "PRIORITY: This workflow OVERRIDES all other built-in workflows". Claude Code would load the root CLAUDE.md and v2's .claude/CLAUDE.md; Copilot would load copilot-instructions.md and AGENTS.md. Two workflows fighting in one context gives unpredictable runs.

ℹ️

Upstream ships no automatic v1 importer; the v2 engine doesn't read aidlc-docs/. The path below is our recommended migration, built on v2 features that are designed for it (DocumentKB ingestion, the memory layer, Reverse Engineering).

✍️ Migrate

Move the team's additions into the v2 memory and knowledge layers

aidlc/spaces/default/memory/team.md (append under existing headings)
## Forbidden - Raw SQL. Use EF Core (compiled queries on hot paths). - Logging PII. Mark sensitive fields with [Sensitive]. ## Mandated - Input validation with FluentValidation. - Azure AD auth on every endpoint unless explicitly [AllowAnonymous]. - Never remove or bypass the Checkmarx SAST stage in a Jenkinsfile.

Org-wide rules (shared across many repos) belong in memory/org.md. It's a project-owned seed, so a refresh never overwrites it. Keep each rule to one imperative line.

PowerShell
PS> mkdir aidlc\spaces\default\knowledge\aidlc-shared, aidlc\spaces\default\knowledge\aidlc-pipeline-deploy-agent # split semantic-context.md by topic, one file per topic PS> code aidlc\spaces\default\knowledge\aidlc-shared\stack-and-patterns.md PS> code aidlc\spaces\default\knowledge\aidlc-pipeline-deploy-agent\jenkins-stages.md
PowerShell, then chat
PS> git mv aidlc-docs docs/aidlc-v1-history > /aidlc knowledge onboard docs/aidlc-v1-history Copied 23 documents into knowledge/documents/aidlc-v1-history/ and indexed them.

The old requirements, stories and designs become citable inputs for new work. The original folder stays as history in git.

✔️

Ask at any gate "What team knowledge are you using for this stage?" to confirm the move worked. /aidlc --doctor also flags team or project rules that drift from org.md.

⏸️ Open work

v2 can't resume a v1 aidlc-state.md, so choose one

Option 1: finish on v1 first

Best if the feature is nearly done. Finish it on the old setup, merge it, then do the migration PR.

Option 2: re-seed in v2

Start a v2 intent that reads the v1 artefacts as input. Approved requirements are re-confirmed quickly; Reverse Engineering sees the code already written.

🔄 Lifecycle

Upgrading from awslabs/aidlc-workflows is two separate steps

The AIDLC files committed in your repo are a projection of a release. Updating the machine doesn't change any repo; refreshing a repo is what rewrites its framework files.

1 · Machine

aidlc update installs the newest stable binary + runtimes. It never installs something older than what's running.

2 · Each project

aidlc config --harness claude --yes, then --harness copilot --yes. Transactional, with an ownership baseline. Done even while work is open.

3 · Teammates

Commit the refreshed files. Others pull; their next chat uses the new release. Plugins: /aidlc plugin sync.

PowerShell: upgrade drill (illustrative)
PS> aidlc update Updated aidlc from 2.11.0 to 2.12.0. PS> aidlc doctor warn Harness trees on different releases: .claude 2.11.0, .aidlc 2.11.0 (engine 2.12.0) fix: aidlc config --harness claude ; aidlc config --harness copilot PS> aidlc config --harness claude --dry-run update .claude/agents/*.md, .claude/hooks/*, .claude/knowledge/**, .claude/scopes/* merge .claude/settings.json (AI-DLC hooks restored; your hook groups appended) preserve aidlc/spaces/default/memory/**, knowledge/**, codekb/**, intents/** remove .claude/skills/aidlc-old-runner/ (no longer shipped) conflict .claude/agents/aidlc-developer-agent.md (locally modified) PS> aidlc config --harness claude --yes Updated. Your open work (default/invoice-export-resume) carries on. To go back: `aidlc config --pin 2.11.0 --yes` (this pins the version for everyone on the project; `aidlc config --unpin` removes the pin). Removed 1 file that is no longer part of AI-DLC 2.12.0: .claude/skills/aidlc-old-runner/ (git restore <path> brings it back)

What a refresh does to each file

Pick a path. Rules come from the upstream Refresh Safety and Root Integrations and Ownership docs for 2.11.

ActionMeaning
updateRefresh framework-owned bytes
mergeReconcile a managed block, JSON map or array; your entries kept
preserveKeep current or project-owned bytes
removeRemove an unchanged framework file the release no longer ships
conflictRefuse: you modified a framework-owned file, or ownership can't be proved

⚠️

The catch with seeds: org.md, team.md and project.md are copied once and then never overwritten. That protects your edits, but it also means new framework defaults a release adds to its shipped org.md don't reach you automatically. Read the release's CHANGELOG and copy any new defaults you want. /aidlc --doctor's rule-drift check helps.

🛟 Safety

Refreshing with work in flight, and going back

  • ✓
    Open work carries on. Since 2.11, any aidlc config run beside open work is done, not refused, and prints what changed and its undo. Existing intents keep their recorded Guard Policy, sensors, learnings and summary confirmation; new 2.11 settings (plan approval, collaborators) follow the scope's new defaults.
  • ✓
    Rollback = pin: aidlc config --pin 2.11.0 --yes (for everyone), aidlc config --unpin to release it. aidlc use 2.11.0 switches your machine.
  • ✓
    Harnesses stay level. Refresh every harness tree in the repo; doctor warns when .claude and .aidlc are on different releases.
  • ✓
    Copy channel (no native binary): replace the whole runtime/<harness>/ tree from aidlc-copy-runtime-X.Y.Z.tar.gz (needs Bun ≥ 1.3.8). The archive deliberately leaves out .gitignore, AGENTS.md, .mcp.json, .vscode/settings.json, your memory files and aidlc/active-space, so copying a newer release over keeps them.
  • ✓
    Plugins: run /aidlc plugin sync after an engine refresh.

Upgrade checklist (per repo)

  1. Read the release notes in CHANGELOG.md: Upgrade, Breaking, Changed default lines.
  2. aidlc update on your machine.
  3. Branch; aidlc config --harness <each> --dry-run; resolve conflicts.
  4. aidlc config --harness <each> --yes; aidlc doctor.
  5. Merge new org defaults you want into memory/org.md.
  6. Smoke run (/aidlc express …) in each tool; commit; PR.
