Step 1
🗺️ Map

The v1 "semantic context" doc is now four things

Everything lives in the active space (aidlc/spaces/default/ for most teams), committed to git, shared by every harness.

📏 memory/ (rules)

Short, prescriptive "always / never" practices. org.md → team.md → project.md → phases/*.md. Every applicable rule reaches every agent.

📚 knowledge/ (reference)

Long-form standards an agent consults: API patterns, coding conventions, SLO definitions. Shared or per-agent folders.

📄 DocumentKB

Your own PDFs, Word files and Markdown (PRDs, policies, briefs) indexed into a catalog agents can cite.

🧩 CodeKB

What each repo is: architecture and component inventory, written by Reverse Engineering, with a freshness marker.

🎯 Quiz

Rule or knowledge? Sort these billing-service standards

Rule of thumb from the upstream docs: if a reviewer would reject a stage's output when it's violated, it's a rule (memory). If they'd use it as background, it's knowledge.

ℹ️

Rules are one line each, imperative. Knowledge can be long prose, tables, diagrams. Neither goes in .claude/ or .aidlc/: those are framework files, overwritten on every upgrade.

Tags may be written by the model from customer content, so list and show present them as untrusted labels, never instructions. Never hand-edit documentkb/; the next sync reconciles it back.

🧩 Code knowledge

Two stages that write knowledge for you

2.1 Reverse Engineering → CodeKB

A two-link pipeline: the developer agent scans the code, the architect synthesises 9 artefacts into codekb/<repo>/ (architecture, component inventory, freshness marker). Later runs do focused rescans that merge new areas without replacing the rest. .NET bin/ and obj/ are skipped.

2.2 Practices Discovery → memory

The pipeline-deploy agent drafts how your team really works from evidence in the repo; quality, developer and devsecops inspect it independently; you're interviewed on gaps; affirmed sections are promoted into memory/team.md or project.md.

memory/team.md (after Practices Discovery affirmation)deterministic section replace
## Testing Posture - Unit tests with xUnit; integration tests against a containerised SQL Server. - PR builds run in Jenkins: Build → UnitTest → SAST (Checkmarx) → Deploy-Dev. ## Code Style - New PDF work uses PdfSharp; iTextSharp is legacy (migrate on touch). ## Guard Policy Mode: strict
ℹ️

CodeKB MCP (optional, external): unrelated to the codekb/ folder. If you connect a CodeKB MCP server, the composer uses its call graphs to score structural uncertainty. Without one it uses the bounded workspace scan, which is the normal path.

📏 Memory

Five layers, strict-additive

org → team → project → phase → stage (the per-stage layer is reserved for a future release). Nothing overrides anything: every applicable rule is in the agent's context. Which files apply is compiled once; their text is re-read before each stage, so a kept learning reaches the very next stage.

🔒

Guard Policy lives here too. A ## Guard Policy section with Mode: strict in any memory file holds strict for everyone on the repo and keeps plan approval on. Mode: relaxed|off sets the default for work whose value came from its scope; the narrowest file wins.

🩺

When org policy changes after a team or project rule exists, /aidlc --doctor shows advisory rule drift: the file, the section and the conflicting org sentence.

🔁 Simulator

Run the learning gate yourself

While a stage runs (learnings on), the agent keeps a diary in <record>/inception/requirements-analysis/memory.md. Before the approval gate a tool lists every diary line verbatim, and you pick what to keep.

Learning gate · Requirements Analysis · billing-service
Anything to add for next time?
  • Interpretations, Deviations and Tradeoffs become practices in memory/project.md (or team.md if promoted). Open questions don't promote.
  • The learning loop never writes org.md.
  • Before writing, the orchestrator compares the entry with the matching org.md section and asks you to revise, skip or escalate if it conflicts.
  • A kept sensor binding installs a sensor manifest and wires it to the stage in one atomic step (SENSOR_PROPOSED).
  • Off for bugfix and express by default; turn it on with /aidlc --learnings on.
🏢 Spaces

When two teams share a repo

Most people only ever see default. A second team gets its own space: its own method, knowledge, CodeKB and intents. It starts from the framework baseline with empty team.md/project.md, so it earns its own practices.

in chat
> /aidlc space create payments-team > /aidlc space switch payments-team > /aidlc intent # list intents in this space > /aidlc intent export-bug # switch to one > /aidlc intent archive old-spike # retire without deleting
ℹ️

Switching writes the new space's memory into a git-ignored aidlc/active-memory/ copy that every harness's include reads, so no tracked file churns. Two simultaneous sessions in different spaces can race on that ambient copy; concurrent intents within one space are fully supported.
